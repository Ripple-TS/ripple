Cheaper component instantiation and `@if` chains on the client. A component call site with a reactive prop now compiles to an instance of a props class built once per call site shape (`_$_.props_site`): the props are prototype getters, the instance holds only the captured locals and static values in symbol slots, and construction is one allocation with no per-property runtime call and no per-getter closure. A reactive prop expression built only from the component's own `props`, constants and captured values is evaluated once and kept when that evaluation read no tracked state, so a prop forwarded down a component tree stops re-evaluating the whole getter chain on every read. Because the props are prototype getters, `Object.keys`, `Object.values`, `Object.entries` and object spread of an object in `.tsrx` code compile to props-aware helpers, props serialize through `toJSON`, and the runtime's spread, rest and dynamic-element helpers read a props instance's full key list; plain `.ts` code should read props by name (or `for...in`), since own-property enumeration of a compiled props instance sees only its static values. A lazy pair's `Tracked` alias passed as a prop is a static value rather than a getter. An `@else if`, and a branch whose only statement is another `@if`, fold into the enclosing `@if` block on both the client and the server, so a chain costs one block and one hydration boundary. A module-level component's render body is a module-level function that receives the props from the element instead of a closure created per instantiation, `Context.get()`/`set()` calls on a `new Context()` binding skip the `with_scope` wrapper, and `mount()` only schedules the SSR style removal when the page has server-rendered inline styles.
